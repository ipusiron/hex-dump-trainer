    パケットの読み方

    IPv4教材の自作フレームを例に、外側のヘッダーから順に読みます。各図の箱の幅はフィールドの長さ、箱内の値は教材の実際の値です。左端はフレーム先頭を0とする10進数のバイト位置です。

    図の項目か解説行にカーソルを合わせると、図・16進ダンプ・解説の対応箇所を強調します。タップで選択でき、同じ項目をもう一度タップすると解除できます。キーボードでは図の項目に移動し、EnterかSpaceで選択できます。

    Ethernet II IPv4 UDP ICMPv4とPing

    3つのヘッダーの境界

    行頭の0010は16進数のオフセットで、10進数では16です。1行に8バイトあるので、行頭だけでフィールドの位置を決めず、バイトを数えます。

    1. 0〜13Ethernet IIヘッダー（14バイト）
    2. 14〜33IPv4ヘッダー（IHL 5 × 4 = 20バイト）
    3. 34〜41UDPヘッダー（8バイト）
    4. 42〜61UDPデータ（20バイト）

    この範囲は掲載例の値です。他の教材もヘッダーの開始位置は同じですが、データの長さは異なります。教材にVLANタグやIPv4オプションはなく、FCSもダンプに含めません。UDPフィールドは演習でも採点します。

    Ethernet II：次のヘッダーを見つける

    最初の6バイトが宛先MACアドレス、次の6バイトが送信元MACアドレスです。続く2バイトのEtherTypeで、後ろに入るデータの種類を確認します。

    0〜5 宛先MAC
    02 FE DC BA 98 76 → 02:FE:DC:BA:98:76
    6〜11 送信元MAC
    02 12 34 56 78 9A → 02:12:34:56:78:9A
    12〜13 EtherType
    08 00を順に読んで0x0800。後続はIPv4で、オフセット14から始まります。

    参照：RFC 894（別タブ）。EthernetでIPv4を運ぶときのType値0x0800と、IPヘッダーをデータ領域の先頭に置く規定を確認できます。

    IPv4：長さと上位プロトコルを読む

    IPv4ヘッダーの先頭は絶対オフセット14です。以下の位置から14を引くと、IPv4ヘッダー内の相対オフセットになります。

    14 Version
    45の上位4ビットが4。IPv4を示します。
    14 IHL
    45の下位4ビットが5。ヘッダー長は5 × 4 = 20バイトです。
    15 ToS
    00。RFC 791の図ではType of Serviceと表記されます。この教材では値の位置を確認します。
    16〜17 Total Length
    00 30 → 0x0030 → 48バイト。IPv4ヘッダーとその後ろのデータを含み、Ethernet IIの14バイトは含みません。
    18〜19 Identification
    30 03 → 0x3003。フラグメントの再構成に使う識別値です。
    20 Flags
    40 00の上位3ビットは010。DFが1、MFが0です。
    20〜21 Fragment Offset
    40 00の下位13ビットは0。分割位置のずれはありません。
    22 TTL
    80 → 10進数で128。転送中に減る寿命の値です。
    23 Protocol
    11 → 10進数で17。後続はUDPです。
    24〜25 Header Checksum
    63 E6。検査対象はIPv4ヘッダーで、UDPデータは含みません。
    26〜29 送信元IP
    C6 33 64 4Dを1バイトずつ10進数へ変換して198.51.100.77。
    30〜33 宛先IP
    CB 00 71 52 → 203.0.113.82。

    この例ではIHLが5なので、UDPは14 + 20 = 34から始まります。IHLが変わるパケットでは、この開始位置も変わります。

    参照：RFC 791（別タブ）のInternet Header Formatで各フィールドの幅と意味を確認できます。Protocol値17の登録はIANA Protocol Numbers（別タブ）を参照してください。

    UDP：ポートとデータ長を読む

    IPv4のProtocolが17なので、IPv4ヘッダーの後ろをUDPとして読みます。この例のUDPヘッダーは絶対オフセット34から8バイトです。

    34〜35 送信元ポート
    D6 D8 → 0xD6D8 → 55000。
    36〜37 宛先ポート
    00 35 → 53。
    38〜39 Length
    00 1C → 28バイト。UDPヘッダー8バイトとデータ20バイトを含みます。
    40〜41 Checksum
    FD 29。計算にはUDPだけでなく、IPv4の送信元アドレスと宛先アドレスなどを含む疑似ヘッダーも使います。

    データはオフセット42からです。ポート番号だけでアプリケーションの内容を断定しないでください。演習ではChecksumフィールドの値を読むだけで、再計算は求めません。

    参照：RFC 768（別タブ）のFormatとFieldsで、4つのUDPフィールドとLengthの範囲、チェックサムの疑似ヘッダーを確認できます。

    ICMPv4 Echo：Pingの往復を読む

    ここからは別の自作フレームです。IPv4のProtocol 01はICMPv4を示します。IHLが5なので、ICMPは絶対オフセット34から始まります。例は同じLAN上の2台の通信です。

    34 Type
    08はEcho Request、応答では00です。
    35 Code
    00。EchoのCodeは0です。
    36〜37 Checksum
    A2 8C。ICMPメッセージ全体を対象とし、応答では再計算します。
    38〜39 Identifier
    12 34 → 0x1234。要求と応答の対応付けに使います。
    40〜41 Sequence Number
    00 01 → 1。応答にも同じ値が入ります。

    42〜59はデータ「PING-LESSON-000001」です。応答はIdentifier・Sequence Number・データをそのまま返し、IPv4の送信元と宛先が逆になります。Typeは00、ICMP ChecksumはAA 8Cに変わります。TTLは両方向で同じとは限りません。

    Pingの往復時間（RTT）は送信側が送信から受信までを計測します。EchoヘッダーにRTTフィールドはありません。この教材は実際のネットワークにPingを送信しません。Time ExceededとICMPv6は別の教材とします。

    参照：RFC 792（別タブ）のEcho or Echo Reply Message、IANA Protocol Numbers（別タブ）。

    Ethernet II IPv4 UDP ICMPv4 and Ping

    Where the three headers begin and end

    The row label 0010 is a hexadecimal offset: 16 in decimal. Each row shows eight bytes, so count the bytes rather than treating a row label as a field boundary.

    1. 0–13Ethernet II header (14 bytes)
    2. 14–33IPv4 header (IHL 5 × 4 = 20 bytes)
    3. 34–41UDP header (8 bytes)
    4. 42–61UDP data (20 bytes)

    These ranges belong to this example. Other lessons share the header start positions but have different data lengths. The lessons contain no VLAN tag or IPv4 options, and the dump omits FCS. UDP fields are also graded in Exercises.

    Ethernet II: find the next header

    The first six bytes hold the destination MAC address, followed by six bytes for the source MAC address. The two-byte EtherType identifies the type of data that follows.

    0–5 Destination MAC
    02 FE DC BA 98 76 → 02:FE:DC:BA:98:76
    6–11 Source MAC
    02 12 34 56 78 9A → 02:12:34:56:78:9A
    12–13 EtherType
    Read 08 00 in order as 0x0800. IPv4 follows at offset 14.

    Reference: RFC 894 (new tab) specifies the Ethernet Type value 0x0800 for IPv4 and places the IP header at the start of the data field.

    IPv4: read length and next protocol

    The IPv4 header starts at absolute offset 14. Subtract 14 from a position below to get its offset relative to the IPv4 header.

    14 Version
    The upper four bits of 45 give 4, indicating IPv4.
    14 IHL
    The lower four bits of 45 give 5. Header length is 5 × 4 = 20 bytes.
    15 ToS
    00. RFC 791 labels this field Type of Service. This lesson uses it to identify the field's position.
    16–17 Total Length
    00 30 → 0x0030 → 48 bytes. This includes the IPv4 header and its data, but not the 14-byte Ethernet II header.
    18–19 Identification
    30 03 → 0x3003. This identifying value aids fragment reassembly.
    20 Flags
    The upper three bits of 40 00 are 010: DF is 1 and MF is 0.
    20–21 Fragment Offset
    The lower 13 bits of 40 00 are 0, so there is no fragment offset.
    22 TTL
    80 → 128 in decimal. This lifetime value is reduced during forwarding.
    23 Protocol
    11 → 17 in decimal, indicating UDP.
    24–25 Header Checksum
    63 E6. It covers the IPv4 header, not the UDP data.
    26–29 Source IP
    Convert each byte of C6 33 64 4D to decimal: 198.51.100.77.
    30–33 Destination IP
    CB 00 71 52 → 203.0.113.82.

    With IHL 5, UDP starts at 14 + 20 = 34. A packet with a different IHL would move this boundary.

    Reference: the Internet Header Format in RFC 791 (new tab) defines these field widths and meanings. See the IANA Protocol Numbers registry (new tab) for the assignment of 17 to UDP.

    UDP: read ports and length

    IPv4 Protocol 17 identifies the next header as UDP. In this example, its eight-byte header begins at absolute offset 34.

    34–35 Source Port
    D6 D8 → 0xD6D8 → 55000.
    36–37 Destination Port
    00 35 → 53.
    38–39 Length
    00 1C → 28 bytes, including the eight-byte UDP header and 20 data bytes.
    40–41 Checksum
    FD 29. Its calculation also uses a pseudo-header containing the IPv4 source and destination addresses, among other values.

    Data begins at offset 42. A port number alone does not establish the application content. Exercises ask you to read the Checksum field, not recalculate it.

    Reference: the Format and Fields sections of RFC 768 (new tab) define the four UDP fields, the Length coverage, and the checksum pseudo-header.

    ICMPv4 Echo: read a Ping exchange

    This uses a separate original frame. IPv4 Protocol 01 identifies ICMPv4. With IHL 5, ICMP starts at absolute offset 34. This is an example of two hosts on the same LAN.

    34 Type
    08 is Echo Request; a reply uses 00.
    35 Code
    00. Echo uses Code 0.
    36–37 Checksum
    A2 8C. It covers the ICMP message and is recomputed for the reply.
    38–39 Identifier
    12 34 → 0x1234. It helps match a reply with its request.
    40–41 Sequence Number
    00 01 → 1. The reply returns the same number.

    Offsets 42–59 hold PING-LESSON-000001. The reply returns the same Identifier, Sequence Number, and data; IPv4 source and destination reverse. Its Type becomes 00 and ICMP Checksum AA 8C. TTL need not be the same in each direction.

    The sender measures round-trip time (RTT) between sending and receiving. RTT is not an Echo header field. This lesson sends no real Ping traffic. Time Exceeded and ICMPv6 are separate future topics.

    References: RFC 792 (new tab), Echo or Echo Reply Message; IANA Protocol Numbers (new tab).
